## 1. 本规格集的地位

### 1.1 三份文档的关系

| 文档 | 回答什么 | 性质 |
|---|---|---|
| `DSH企业级技术方案设计.md` v2.6 | **为什么这样设计**（架构、取舍、约束来源） | 设计依据 |
| `DSH架构多角色评审汇总.md` | **为什么改**（问题、根因、修订） | 历史依据 |
| **本规格集 `spec/`** | **开发必须做成什么样**（可执行、可验收的条款） | **开发约束** |

### 1.2 权威顺序（冲突时）

```
SPEC-00（本总纲）
  > 各角色规格（SPEC-01…05）
    > 设计文档 v2.6
      > 评审汇总（仅作历史依据，不构成约束）
```

**重要规则**：若某角色规格与设计文档**实质冲突**（不是细化而是矛盾），**不得由开发者自行选择**。必须：
1. 记录冲突（文件 + 小节 + 双方原文）
2. 提给总纲维护者
3. **改文档后同步规格**，或**改规格后回溯文档**

> **禁止**：绕过规格直接按设计文档实现；也禁止按规格实现而文档明显写反了却不改文档。

### 1.3 规格集不覆盖的内容

- DSH 内核自身的功能开发
- 供应商选型（IdP、密钥库、云厂商）
- 具体排期与人力（见 `SPEC-03` 的工作量量级，仅作估算输入）

## 3. 规范用语

| 用语 | 含义 | 违反后果 |
|---|---|---|
| **必须**（MUST） | 无条件要求 | 阻断：不得合并 / 不得发布 |
| **不得**（MUST NOT） | 无条件禁止 | 阻断 |
| **应当**（SHOULD） | 有充分理由可偏离，但须书面记录偏离理由与补偿 | 需评审签署 |
| **可以**（MAY） | 可选 | 无 |

**禁止使用"建议""尽量""最好"等无约束力措辞**来描述强制要求。

## 4. 需求 ID 方案

### 4.1 编号段（固定分配，不得越界）

| 段 | 归属 | 格式 |
|---|---|---|
| `SEC-###` | `SPEC-01` 安全与合规 | 三位数字，从 `001` 起 |
| `REL-###` | `SPEC-02` 可靠性 | 同上 |
| `ENG-###` | `SPEC-03` 工程实现 | 同上 |
| `PRD-###` | `SPEC-04` 产品与商业 | 同上 |
| `EVO-###` | `SPEC-05` 演进与生命周期 | 同上 |
| `GATE-###` | `SPEC-00` 阶段门禁（仅总纲分配） | 同上 |

### 4.2 编号规则

1. **只增不改号**。删除一条需求时**保留编号**并标注 `[已废止 vX.Y]` + 废止理由，**不得复用**。
2. 一条需求一个可独立验收的约束。**禁止**把多个不相关要求塞进一条。
3. 每条需求**必须**能追溯到设计文档的 `C##` / `D##` / `G##` 或具体小节；无法追溯的条款**不得写入规格**（说明它没有设计依据，应先改设计）。

### 4.3 跨规格引用

**唯一合法形式**：`见 SEC-014` / `依赖 ENG-007`。
**禁止**：`见《安全规格》第 3 节`（文件与小节会变，ID 不会）。

## 5. 每条需求的必备字段

每条需求**必须**是如下表格的一行，或如下结构的条目。缺字段的需求**不予受理**。

| 字段 | 说明 |
|---|---|
| **ID** | 见 §4 |
| **级别** | 必须 / 不得 / 应当 / 可以 |
| **条款** | 一句话可判定陈述。**必须可判定**——"性能要好"不合规，"P95 ≤ 400 ms"合规 |
| **验收判据** | 怎么证明它成立。**禁止**写"通过测试"这类同义反复 |
| **依据** | 设计文档的 `C##` / `D##` / `G##` / 小节号 |
| **拦截点 / 测量点** | 该约束在**哪一处**被强制或被测。无拦截点者**必须**标注为 detective 或降级为 `应当` |

> **第 6 个字段是本规格集的硬性要求**。它来自设计文档的 **D15/D16**：
> 声明式的约束不构成强制；**没有拦截点的"必须"是空话**。

## 8. 变更控制

| 变更类型 | 流程 |
|---|---|
| 新增需求 | 提给总纲维护者分配 ID；须有设计依据或先改设计 |
| 修改条款 | 改版本号 + 记变更记录；影响验收判据时须重跑对应门禁 |
| 删除需求 | **保留编号**并标 `[已废止]` + 理由；不得复用编号 |
| 规格间冲突 | 由总纲维护者裁定；**不得**两处各写一份 |

**版本号规则**：`主版本.次版本`。新增或修改条款 → 次版本 +1；改变权威顺序、ID 方案或门禁定义 → 主版本 +1。
