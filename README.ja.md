# DSH-BOOT

> **DSH カーネルの上に構築する、エンタープライズ級 AI Agent プラットフォーム。**
> あなたが書くのはビジネスロジックだけ。マルチテナント分離、セキュリティ監査、承認、クォータと課金、セッション永続化、進化互換性——これらはすべてプラットフォームが提供し、契約テストで固定します。自分で書く必要はありません。

## なぜこのプロジェクトが生まれたのか

DSH がオープンソース化された後、私はずっと一つの問題を考えていました：**DSH の能力をエンタープライズアプリケーションにどう取り込むか？**

すべての会社が完全な AI Agent プラットフォームを開発できるわけではない。しかし AI 時代において、すべての会社に共通する願いがあります——自社のビジネスシナリオを AI と結合し、ローカルサービスの構築とクラウドデプロイを行うことです。

DeepSeek harness 自体はこれらの具体的なことを行いません。「すべてはプラグイン」という理念に基づき、DSH は自由に使えて著作権リスクのない harness ベースプラットフォームとして捉えることができ、しかもこのベースは技術の最前線で進化し続けています——企業が新しい技術を追いかけるさまざまなコストを、これで省けます。

DSH は単一 Agent のランタイムを非常にうまく作っています——ツールサンドボックス、承認ウォーターフォール、プリセットとプラグインエコシステムは、箱から出してすぐ使えます。しかしエンタープライズアプリケーションに必要なのはそれだけではありません：マルチテナントをどう分離するか？監査をどう改ざん不能にするか？ユーザーがデータ削除を求めたら？あるテナントがリソースを使い果たしたら？アップグレードで顧客データを壊さないには？——これらは DSH カーネルにはなく、各社がゼロから作れば同じ轍を踏みます。

その探索の結論：**DSH をカーネルとする harness プラットフォームが必要**です。DSH カーネルはすでに 3 つの境界のうち 2 つ（能力境界・呼び出し境界）を提供しており、欠けているのは最外層（テナント/リソース分離）だけ——だからこのプロジェクトは DSH を書き直さず、その上に外層を補完し、内層と中層を固定します。

目標：**企業がビジネス実装に集中しながら、DSH の先進的な理念の恩恵を最大限享受できること**——シナリオ・ツール・コネクタ・スキルを定義すれば、分離・監査・承認・クォータと課金・永続化とリカバリ・進化互換性はプラットフォームが担い、その約束はすべて契約テストで固定されます。DSH をアップグレードするかどうか、いつするかもあなたの判断です：アップグレードは 5 つのゲートを持つパイプライン（契約テスト、スナップショット diff、列車整合性、カナリア記録、準備完了再検証）を通過して平滑に行われ、ビジネスに影響しません。

## ビジネスシステムは 3 層で構成される

ビジネスシステムの 1 セッションは、上から下へ 3 つの層を通過します：

```
あなたのユーザー
   │
   ▼
┌──────────────────────────────────────────────┐
│ ビジネスシステム（あなたが書く）              │
│ あなたの UI（Web/App/CLI）+ ビジネスフロー    │
│ + シナリオ・ツール・コネクタ・スキル          │
└──────────────────┬───────────────────────────┘
                   │ プラットフォーム API でセッション/ターンを開始
                   ▼
┌──────────────────────────────────────────────┐
│ DSH-BOOT（本プロジェクト、プラットフォーム層）│
│ 認証 · クォータと課金 · 承認 · 監査フォレンジック│
│ DSR 削除 · デグレード · アップグレードゲート  │
└──────────────────┬───────────────────────────┘
                   │ ターンを分離ドメインへディスパッチ
                   ▼
┌──────────────────────────────────────────────┐
│ DSH カーネル（分離ドメインごとに 1 インスタンス）│
│ モデル呼び出し · ツール実行 · サンドボックス · プラグイン│
└──────────────────────────────────────────────┘
```

| 層 | 提供者 | あなたの作業 |
|---|---|---|
| **ビジネスシステム** | **あなた**：UI、ビジネスフロー、定義するシナリオ/ツール/コネクタ/スキル | 4 種類のアセットを定義 + プラットフォーム API 呼び出し。UI はビジネス形態に応じて（Web/App/CLI いずれも可） |
| **DSH-BOOT** | **本リポジトリ**（実装済み、契約テストで固定）：マルチテナント、監査、クォータと課金、DSR、デグレード、アップグレードゲート | デプロイ時にインフラ（Linux コンテナランタイム、エンタープライズ IdP、オブジェクトストレージ）を接続・設定 |
| **DSH カーネル** | **DSH オープンソースカーネル**（未改変）：単一 Agent ランタイム | なし——バージョン、準備完了、ドリフトは DSH-BOOT が管理 |

セキュリティの観点では、この 3 層は**3 つの境界**に対応します：内層の能力境界と中層の呼び出し境界は DSH カーネルと DSH-BOOT が共同で守り、外層のテナント/リソース分離は DSH-BOOT が提供します——下表をご覧ください。

## DSH-BOOT と DSH の関係：3 つの境界、欠けているのは最外層だけ

DSH カーネルは単一 Agent に完全なランタイムを与えます：モデル呼び出し（`ctx.llm`）、ツール登録（`ctx.tools`）、承認ウォーターフォール（`ctx.approval`）、サンドボックス（`dsh-sandbox*`）、プリセット（`dsh-agent-preset`）。しかし 3 つの境界のうち**2 つしか提供していません**——欠けているのは、マルチテナントに最も必要な外層です：

| 境界 | 性質 | DSH カーネル | DSH-BOOT の対応 |
|---|---|---|---|
| **内層：能力境界** | この Agent がどのツール/プラグインを持つか | ✅ `dsh-agent-preset` + scope | **固定 + ドメイン外統治**：ツール登録ブリッジが唯一の入口（toolAllowlist 外は一切登録されない）；単一プリセット + 昇格上限；Plugin/Connector/Skill/Scenario の 4 カタログで、階層の合法性をドメイン外の Profile 生成時に判定——**テナント定義プラグインはプラットフォーム固定層に入れない** |
| **中層：呼び出し境界** | 呼び出しごとのファイル書き込みポリシー + 承認ウォーターフォール | ⚠️ あるが Windows 檔は partial | **補完 + 実測**：承認レスポンダー + 10 フィールドのパラメータチャネル（マスキング/切り詰め/順序付け）+ 3 層デッドライン（`T_a`/`T_m`/`T_turn`）；Windows コンテナ内 ACL 実測の結果**不成立と判定 → Windows はマルチテナント分離から除外** |
| **外層：テナント/リソース分離** | カーネルレベルのマルチテナント | ❌ なし | **自作（本プロジェクトの主体）**：3 状態のドメインプール（hot/warm/cold）、`(tenantId, isolationGroupId)` にバインドされたドメイントークン、workspace 排他リース、ID/RBAC/クォータ/フェアスケジューリング/課金、SessionPersistence L1/L2 + 移行ステートマシン、fail-closed 監査 + WORM ハッシュチェーン、DSR 削除証明、デグレードラダー |

**3 つの層が揃って、マルチテナントが成立します。** 内層（Agent がどのツールを持つか）だけで分離を宣言するのは、能力境界を安全境界に見立てることです——これが本プロジェクトのすべてのアーキテクチャ判断の起点です。

では DSH-BOOT とは何か？それは**マルチテナント AI Agent プラットフォームソフトウェア**であり、3 つの部分から成ります：

1. **コントロールプレーンサービス**（TypeScript パッケージ）：ID と RBAC、クォータとフェアスケジューリング、課金取り込み、監査とフォレンジック、DSR 削除、セッションルーティングとインデックス——エンタープライズプラットフォームのバックオフィスロジック；
2. **DSH 統合**（リバースゲートウェイスタブ + ドメインブリッジ）：DSH のモデル呼び出し・ツール登録・承認ウォーターフォールをコントロールプレーンに接続し、ドメイン外でアーティファクト検証とドリフト検出を行う——DSH カーネルは未改変；
3. **エンジニアリングゲート**（仕様セット + 検証ツール）：397 の要求、6 つのゲート、スナップショット diff——上記の約束が後の変更で静かに壊されないことを保証します。

DSH を書き直すのではない：各 Agent は依然として DSH カーネルで実行され、DSH-BOOT はそのような Agent の集合を 1 社のマルチテナントプラットフォームとして管理します。デプロイ形態：コントロールプレーンサービス + 分離ドメインごとに 1 つの DSH インスタンス（Linux コンテナ）+ ゲートウェイ。

### DSH-BOOT と DSH の間で何がやり取りされるか

各分離ドメインには 1 つの DSH インスタンスが動き、両者を繋ぐのは明確に定義されただけのチャネルです：

| 相互作用 | 方向 | 内容 |
|---|---|---|
| **Profile 配信** | ドメイン外 → 内 | 定義したシナリオ/ツール/コネクタ/スキルは、Profile ジェネレーター（ドメイン外）が `pluginSet`・`toolAllowlist`・`skillRoots` を生成し、読み取り専用で DSH インスタンスにマウント |
| **プラグイン/アーティファクト登録** | ドメイン外 | プラグインは Plugin Registry に登録（バージョン・署名・整合性ハッシュ）；合法性はドメイン外で判定されてから Profile に入る——**ドメイン内に「プラグインを入れる」操作は存在しない** |
| **ツール登録** | ドメイン内 | DSH 起動後の唯一の入口は `ctx.tools.register` で、`toolAllowlist` 内のみ通過；実行時、ドメイン内からツールマニフェストのハッシュを報告し、ドメイン外で照合——一致しなければドメインを切り離す |
| **モデル呼び出し** | ドメイン内 → 外 | `ctx.llm` 呼び出しはリバースゲートウェイ経由でドメイン外へ：資格情報はドメイン外でブローカーされ、トークン使用量はドメイン外で計量・課金 |
| **承認** | ドメイン内 → 外 | 危険な操作は承認を發起し、ドメイン外のレスポンダーが応答；パラメータはチャネル（マスキング/切り詰め/順序付け）で送られ、3 層デッドライン内に収束しなければならない |
| **資格情報** | ドメイン外 → 内 | MCP コネクタは短命 TTL の資格情報参照のみ受け取り、ドメイン内に長期資格情報は存在しない |
| **セッション永続化** | ドメイン内 → 外 | セッションログはドメイン内のローカルボリュームに書かれ、ドメイン外は「アップロード確認ウォーターマーク」に従って消費——クォータ・課金・監査の真の源 |

一言で言えば：**ドメイン内は実行だけ、判断はドメイン外**。DSH インスタンスは他のテナントの存在を知りません；テナントをまたぐすべての判断（誰が入れるか、何を使えるか、何をしたか、どう削除するか）は DSH-BOOT 側にあります。

一行の類比：**DSH と DSH-BOOT の関係は、JVM と Spring Boot の関係にほぼ相当**——カーネルは単一インスタンスのランタイムを、プラットフォームはマルチテナントのエンタープライズセマンティクスを担います。

## 用語を先に整理

本リポジトリ（と DSH 設計）で繰り返し使われる概念：

- **ドメイン（分離ドメイン）**：あるテナントの分離グループに仕える 1 つの DSH インスタンスが動く、隔離された実行環境（本番では独立コンテナ内）。ドメイン同士は互いに見えない——これがマルチテナント分離の単位です。
- **ドメイン内 / ドメイン外**：ドメイン内 = DSH インスタンスの内部で、モデルとツールが実行される**信頼できない**場所（プロンプトインジェクションや改変の恐れ）；ドメイン外 = dsh-boot のコントロールプレーンとゲートウェイ側で、**信頼できる**場所。だからこそ、認可・監査・アーティファクト検証・準備完了判定はすべてドメイン外で行われ、ドメイン内の報告は参照にすぎません——これを「強制力はドメイン外からのみ」と呼びます。
- **ゲート（GATE）**：次の段階に入る前の強制チェックポイント。各ゲートには実行可能な検証（契約テスト・演習・実測）とアーカイブされた証拠があります；通らなければ停止——署名での通過はありません。
- **契約テスト**：プラットフォームの約束（「テナントは互いに見えない」「承認失敗で自動リトライしない」「ちぎれた末尾は決してユーザーに届かない」）を自動テストとして書き固定。後の変更が約束を壊せば、テストが即座に赤になります。

## もう自分で解決しなくていいこと

| エンタープライズの課題 | DSH-BOOT が提供するもの |
|---|---|
| マルチテナント分離 | `(tenantId, isolationGroupId)` ごとに 1 ドメイン、テナント間は決して共有しない；workspace 排他リース（fencing epoch、移転可能）；ドメイン内の読み取り非分離の限界は正直に開示——need-to-know の顧客はチーム/ユーザーレベルの分離グループを利用 |
| 誰が何をできるか | JWT（エンタープライズ IdP と OIDC 対応）+ RBAC でシナリオ・プラグイン・ツール・MCP・サンドボックスモードの上限をテナント/ロール別に制御；SSO/SCIM 自動オンボーディング、アカウント無効化後 5 分以内にセッションとトークンを全失効 |
| 改ざんできない監査 | 最小監査セット 6 クラス **fail-closed**（記録できなければその操作を拒否）；WORM + ハッシュチェーン；5 項目の監査キー；フォレンジックパックはエクスポート可能・独立検証可能 |
| ユーザーからの削除要求 | DSR フルリスト削除（ログ・添付・FTS・スナップショット・オブジェクトストアバージョン・コンテナ一時層）+ 墓石 + 削除レポート + ハッシュチェーン証明；24 時間以内に発効、取消猶予 7 日 |
| リソースの占有 | 段階的クォータ（ソフト/ハード）+ フェアスケジューリング：上限超過テナントは**比例してスロットリング**され、他のテナントは影響を受けない；ソフト依存の障害が実行を阻断することはない |
| 依存が死んだら | デグレードラダー L0/L1/L1b/L2/L3：進入・退出しきい値、ヒステリシスと最短滞留、テナント別集約アラート、エラーバジェットと凍結リスト |
| アップグレードで顧客データを壊す | 5 状態の移行ステートマシン + `targetBaseSeq == sourceLastReplicatedSeq` アサーションでちぎれた末尾を防止；真の源 = ログ + アップロード確認ウォーターマーク；5 ゲートのアップグレードパイプライン + 前提モニタリング項目の逐次再検証 |
| コンプライアンスの証明 | フォレンジックパック + 削除証明 + ハッシュチェーン、すべてエクスポート可能・独立検証可能 |

## ビジネスシステムの構築

DSH-BOOT 上でのビジネスシステム開発 = 4 種類のアセットを定義すること。それ以外はプラットフォームが担います：

| 定義するもの | 方法 | プラットフォームの保証 |
|---|---|---|
| **シナリオ** | `presetId + pluginSet + policies` | presetId は追加のみ（永続互換面） |
| **ツール** | 登録ブリッジの唯一の入口；toolAllowlist 外は一切登録されない | 悪意ある MCP が新しいツールを押し込んでも可視セットには入れない |
| **コネクタ** | カタログ登録、デフォルト `untrusted` | 資格情報は参照のみ保存；例外はセキュリティレビューが必要 |
| **スキル** | platform / tenant / user の 3 スコープ | テナント別にアセンブル、階層を越えない |

最小例（契約テストからの抜粋、コピーして実行可能）：

```js
import { ScenarioCatalog, ConnectorRegistry } from "../../../../packages/control-plane/src/registry/registries.ts";

// シナリオを定義：presetId + プラグインセット + ポリシー
const scenarios = new ScenarioCatalog();
scenarios.define({
  presetId: "preset-1",
  pluginSet: ["dsh-base"],
  policies: { requireApproval: ["shell"], toolAllowlist: ["fs"] },
});

// MCP コネクタを登録：デフォルト untrusted、例外はセキュリティレビューが必要
const registry = new ConnectorRegistry(2);
registry.register({
  serverName: "github-mcp",
  transport: "stdio",
  hosting: "domain",
  credentialRef: "credref-1",
  trust: "untrusted",
  securityReviewPassed: false,
});
```

ビジネス開発者は**分離・監査・クォータ・永続化のコードを一切書きません**——4 種類のアセットを定義すれば、残りはプラットフォームが提供します。

```bash
# 11 の契約スイート——プラットフォームの約束はすべてテストで固定
pnpm contract:llm && pnpm contract:tools && pnpm contract:approval
pnpm contract:ready && pnpm contract:persistence-l1 && pnpm contract:pool
pnpm contract:identity-quota && pnpm contract:registry
pnpm contract:session-ops && pnpm contract:lifecycle

# 仕様とドキュメントの検証
node tools/lint-specs.mjs && node tools/check-gates.mjs
node tools/validate-contracts.mjs && node tools/lint-docs.mjs
```

## 設計原則

1. **強制力はドメイン外からのみ**——階層の合法性は Profile 生成時に判定され、ドメイン内で自己証明しない（ドメイン内の自己証明コンプライアンスは不成立）。
2. **ゲートはドメイン外の事実のみ受け入れる**——ドメイン内の報告はクロスチェックにすぎず、不一致ならドメインを切り離す。
3. **ソフト依存は決して実行を阻断しない**——課金や一般監査が落ちても実行は継続；有界ドロップ + 墓石 + 再アップロード。
4. **できないことはできないと言う**——未完了項目はすべて正直に記録し、数字を捏造しない。

## 現在の状態と境界（正直版）

- ✅ 6 つの段階ゲート（GATE-001…006）はすべて到達可能で、各自の証拠アーティファクトあり；11 の契約スイート全緑。
- ❌ **Windows はマルチテナント分離から除外**：コンテナ内 ACL 実測が不成立（GATE-002 条件 9、正直に fail と記録）。
- 🔶 **演習 3/6**：DRL-03/04/06 はカーネル内コンポーネントとマルチノードトポロジーが必要で、正直に blocked。
- 🔶 **負荷テストパラメータ未回填**：`PP-01…PP-35` はすべて「例示導出値 + 負荷テスト待ち」——数字は捏造しない。
- 🚫 **UI なし**：本リポジトリはライブラリと HTTP API（ゲートウェイスタブ）を提供し、プロダクト UI は含まない。
