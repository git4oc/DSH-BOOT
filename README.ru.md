# DSH-BOOT

> **Платформа для построения корпоративных AI Agent-систем поверх ядра DSH.**
> Вы пишете только бизнес-логику. Мультитенантная изоляция, аудит безопасности, одобрения, квоты и биллинг, персистентность сессий, совместимость при эволюции — всё это реализует платформа и фиксирует контрактными тестами; писать это самому не нужно.

## Почему существует этот проект

После открытия исходников DSH я постоянно думал над одним вопросом: **как перенести возможности DSH в корпоративные приложения?**

Я всегда считал, что не каждая компания способна разработать полноценную платформу AI-агентов; но в эпоху ИИ у всех компаний одно и то же устремление — объединить свои бизнес-сценарии с ИИ, строя локализованные сервисы и облачные развёртывания.

DeepSeek harness не занимается такими конкретными вещами. Опираясь на его философию «всё — плагин», мы можем использовать его как базовую harness-платформу, свободную в использовании и без рисков с авторскими правами, причём эта платформа стоит на переднем крае технологий и непрерывно эволюционирует — это избавляет компании от многих издержек погони за новыми технологиями.

DSH отлично справляется с рантаймом одиночного агента — песочница инструментов, каскад одобрений, пресеты и экосистема плагинов доступны из коробки. Но корпоративным приложениям нужно больше: как изолировать тенантов? Как сделать аудит неоспоримым? Что делать, если пользователь требует удалить свои данные? Что если кто-то выест все ресурсы? Как обновиться, не сломав данные клиентов? — этого в ядре DSH нет, и каждая компания, строя это заново, наступает на одни и те же грабли.

Вывод из этого исследования: **нужна harness-платформа с DSH в качестве ядра**. Ядро DSH уже даёт две границы из трёх (граница способностей, граница вызовов), не хватает только самой внешней (изоляция тенантов/ресурсов) — поэтому этот проект не переписывает DSH, а достраивает внешний слой поверх него и фиксирует внутренний и средний, превращая «трудное, но правильное» в корпоративном ПО в код платформы.

Цель: **чтобы компании, сосредоточившись на реализации бизнеса, в полной мере пользовались дивидендами передовых идей DSH** — вы определяете сценарии, инструменты, коннекторы и навыки; изоляция, аудит, одобрения, квоты и биллинг, персистентность и восстановление, совместимость при эволюции подстраховываются платформой, и каждое обещание зафиксировано контрактными тестами. Обновлять ли DSH и когда — тоже решаете вы по обстоятельствам: обновление гладко проходит конвейер из пяти гейтов (контрактные тесты, diff снапшотов, консистентность релизного поезда, canary-записи, повторная верификация готовности), бизнес не затронут.

## Что вам больше не нужно решать самим

| Корпоративная проблема | Что даёт DSH-BOOT |
|---|---|
| Мультитенантная изоляция | Один `(tenantId, isolationGroupId)` — один домен изоляции, тенанты никогда ничем не делятся; эксклюзивные аренды workspace (с передаваемым fencing epoch); границы отсутствия изоляции чтения внутри домена раскрыты честно — клиентам need-to-know выделяются группы изоляции уровня команды/пользователя |
| Кто что может | JWT (OIDC к корпоративному IdP) + RBAC: по тенанту/роли управляются сценарии, плагины, инструменты, MCP и потолки режимов песочницы; SSO/SCIM подключается автоматически, после деактивации аккаунта сессии и токены полностью недействительны в течение 5 минут |
| Содеянное не оспорить | Минимальный набор аудита из шести классов — **fail-closed** (нельзя записать — действие отклоняется); WORM + хеш-цепочка; пятиэлементные ключи аудита; форензик-пакеты экспортируемые и проверяемые независимо |
| Пользователь требует удалить данные | Полное DSR-удаление по всему списку (логи/вложения/FTS/снапшоты/версии в объектном хранилище/временные слои контейнеров) + tombstone-записи + отчёты об удалении + доказательства хеш-цепочкой; вступает в силу ≤ 24 ч, окно отзыва — 7 дней |
| Кто-то выедает ресурсы | Уровневые квоты (мягкие/жёсткие) + справедливое планирование: превысившие квоту тенанты **ограничиваются пропорционально**, остальные не затронуты; сбои мягких зависимостей никогда не блокируют выполнение |
| Что если зависимость упала | Лестница деградации L0/L1/L1b/L2/L3: пороги входа/выхода, гистерезис и минимальное время пребывания, агрегированные по тенантам оповещения, бюджеты ошибок и списки заморозки |
| Обновление ломает данные клиентов | Конечный автомат миграции с пятью состояниями + утверждение `targetBaseSeq == sourceLastReplicatedSeq` против разорванного хвоста; источник истины = лог + watermark подтверждённой загрузки; конвейер обновления из пяти гейтов с поэтапной перепроверкой предварительных метрик |
| Комплаенс требует доказательств | Форензик-пакеты + доказательства удаления + хеш-цепочки, всё экспортируемое и проверяемое независимо |

## Сначала поясним несколько терминов

В этом репозитории и в дизайне DSH раз за разом используются эти понятия:

- **Домен (isolation domain)**: одна изолированная среда выполнения, где работает экземпляр DSH, обслуживающий одну группу изоляции одного тенанта (в продакшне — в отдельном контейнере). Домены невидимы друг для друга — это базовая единица мультитенантной изоляции.
- **Внутри / вне домена**: внутри = внутри экземпляра DSH, где выполняются модель и инструменты, — **недоверенная** зона (уязвима к prompt-инъекциям или подмене); вне = плоскость управления dsh-boot и сторона шлюза — **доверенная**. Поэтому авторизация, аудит, проверка артефактов и вердикты готовности выполняются вне домена, а отчёты изнутри домена — только перекрёстная сверка; это называется «принуждение исходит только извне домена».
- **Гейт (GATE)**: обязательная контрольная точка перед переходом к следующему этапу. У каждого гейта есть исполняемые проверки (контрактные тесты, учения, живые испытания) и архивированные доказательства; не пройдено — стоп, никакой подписи «на проход».
- **Контрактные тесты**: каждое обещание платформы («тенанты невидимы друг для друга», «неудавшееся одобрение никогда не повторяется автоматически», «разорванный хвост никогда не доходит до пользователя») записано автоматизированным тестом. Любое последующее изменение, ломающее обещание, немедленно делает тест красным.

## Одна бизнес-система — три слоя

Одна сессия вашей бизнес-системы проходит три слоя сверху вниз:

```
Ваши пользователи
   │
   ▼
┌──────────────────────────────────────────────┐
│ Бизнес-система (пишете вы)                   │
│ Ваш интерфейс (Web/App/CLI) + бизнес-процессы│
│ + сценарии, инструменты, коннекторы, навыки  │
└──────────────────┬──────────────────────────┘
                   │ Вызов API платформы: старт сессии/хода
                   ▼
┌──────────────────────────────────────────────┐
│ DSH-BOOT (этот проект, платформенный слой)   │
│ Авторизация · квоты · одобрения · аудит ·    │
│ форензика · DSR-удаление · деградация ·      │
│ гейты обновления                             │
└──────────────────┬──────────────────────────┘
                   │ Отправка хода в домен изоляции
                   ▼
┌──────────────────────────────────────────────┐
│ DSH-ядро (экземпляр на каждый домен)         │
│ Вызовы модели · инструменты · песочница ·    │
│ плагины                                      │
└──────────────────────────────────────────────┘
```

| Слой | Кто предоставляет | Что делаете вы |
|---|---|---|
| **Бизнес-система** | **Пишете вы**: интерфейс, бизнес-процессы, а также определяемые вами сценарии/инструменты/коннекторы/навыки | Определяете четыре типа активов + вызываете API платформы; интерфейс следует вашей форме бизнеса (Web/App/CLI — любой) |
| **DSH-BOOT** | **Этот репозиторий** (реализовано, зафиксировано контрактными тестами): мультитенантность, аудит, квоты и биллинг, DSR, деградация, гейты обновления | При развёртывании подключаете инфраструктуру (Linux-контейнерный рантайм, корпоративный IdP, объектное хранилище) и конфигурируете её |
| **Ядро DSH** | **Опенсорсное ядро DSH** (без изменений): рантайм одиночного агента | Ничего — версии, готовность и дрейф DSH-BOOT управляет за вас |

С точки зрения безопасности этим трём слоям соответствуют **три границы**: внутренняя граница способностей и средняя граница вызовов охраняются совместно ядром DSH и DSH-BOOT, внешняя изоляция тенантов/ресурсов предоставляется DSH-BOOT — по слоям см. таблицу ниже.

## Отношения DSH-BOOT и DSH: три границы, не хватает только внешней

Ядро DSH даёт одиночному агенту полный рантайм: вызовы модели (`ctx.llm`), регистрацию инструментов (`ctx.tools`), каскад одобрений (`ctx.approval`), песочницу (`dsh-sandbox*`), пресеты (`dsh-agent-preset`). Но из трёх границ **оно даёт только две** — и не хватает ровно той внешней, которая нужнее всего мультитенантности:

| Граница | Характер границы | Ядро DSH | Что сделал DSH-BOOT |
|---|---|---|---|
| **Внутренняя: способности** | Какие инструменты/плагины есть у этого агента | ✅ `dsh-agent-preset` + scope | **Фиксация + управление вне домена**: мост регистрации инструментов — единственная точка входа (всё вне `toolAllowlist` не регистрируется вовсе); единственный пресет + потолок привилегий; четыре каталога Plugin/Connector/Skill/Scenario, легитимность по слоям определяется вне домена при генерации Profile — **тенантские плагины не могут попасть на заблокированный платформой уровень** |
| **Средняя: вызовы** | Политика записи файлов на один вызов + каскад одобрений | ⚠️ Есть, но Windows-слой частичен | **Дополнение + живые испытания**: responder одобрений + десятиполевой канал параметров (маскирование/усечение/упорядочивание) + трёхуровневые дедлайны (`T_a`/`T_m`/`T_turn`); живое ACL-тестирование внутри контейнера на Windows **честно провалилось → Windows запрещена в мультитенантной изоляции** |
| **Внешняя: изоляция тенантов/ресурсов** | Мультитенантность уровня ядра | ❌ Нет | **Построено с нуля (основная часть этой работы)**: пул доменов изоляции в трёх состояниях (горячий/тёплый/холодный), привязка доменных токенов к `(tenantId, isolationGroupId)`, эксклюзивные аренды workspace, идентификация/RBAC/квоты/справедливое планирование/биллинг, SessionPersistence L1/L2 + конечный автомат миграции, аудит fail-closed + WORM-хеш-цепочка, доказательства DSR-удаления, лестница деградации |

**Мультитенантность реальна только при всех трёх границах.** Обещать изоляцию, опираясь лишь на внутреннюю (какие инструменты у агента), — значит выдавать «границу способностей» за «границу безопасности» — с этого начинается каждое архитектурное решение данного проекта.

Так что же такое DSH-BOOT? Это **мультитенантная AI Agent-платформа** из трёх частей:

1. **Сервисы плоскости управления** (пакеты TypeScript): идентификация и RBAC, квоты и справедливое планирование, агрегация биллинга, аудит и форензика, DSR-удаление, маршрутизация и индексация сессий — закулисная логика корпоративной платформы;
2. **Интеграция DSH** (заглушка обратного шлюза + доменный мост): подключает вызовы модели, регистрацию инструментов и каскад одобрений DSH к плоскости управления и вне домена выполняет проверку артефактов и детекцию дрейфа — без модификации ядра DSH;
3. **Инженерные гейты** (набор спецификаций + валидационные инструменты): 397 требований, шесть гейтов, diff-снапшоты — чтобы ни одно из обещаний выше не было тихо сломано последующими изменениями.

Он не переписывает DSH: каждый агент по-прежнему работает на ядре DSH; DSH-BOOT управляет множеством таких агентов как мультитенантной платформой одного предприятия. Форма развёртывания: сервисы плоскости управления + один экземпляр DSH на домен изоляции (Linux-контейнеры) + шлюз.

### Взаимодействие между DSH-BOOT и DSH

В каждом домене изоляции работает один экземпляр DSH, и связывают их лишь несколько чётко очерченных каналов:

| Взаимодействие | Направление | Содержание |
|---|---|---|
| **Раздача Profile** | вне → внутрь | Определяемые вами сценарии/инструменты/коннекторы/навыки генератор Profile (вне домена) превращает в `pluginSet`, `toolAllowlist`, `skillRoots`, и они монтируются в экземпляр DSH только для чтения |
| **Регистрация плагинов/артефактов** | вне | Плагины регистрируются в Plugin Registry (версия, подпись, хеш целостности); легитимность определяется вне домена и только затем попадает в Profile — **внутри домена нет действия «установить плагин»** |
| **Регистрация инструментов** | внутрь | После старта DSH единственная точка входа — `ctx.tools.register`, и пропускает она только имена из белого списка `toolAllowlist`; в рантайме домен сообщает хеш манифеста инструментов, снаружи он сверяется — расхождение, и домен отсоединяется |
| **Вызовы модели** | внутрь → вне | Вызовы `ctx.llm` покидают домен через обратный шлюз: учётные данные выдаются прокси снаружи, расход токенов учитывается и тарифицируется снаружи |
| **Одобрения** | внутрь → вне | Опасные действия инициируют одобрение, снаружи отвечает responder; параметры доставляются каналом (маскирование/усечение/упорядочивание) и обязаны сойтись в пределах трёхуровневого дедлайна |
| **Учётные данные** | вне → внутрь | MCP-коннекторы получают только короткоживущие (короткий TTL) ссылки на учётные данные; долгоживущих учётных данных внутри домена нет |
| **Персистентность сессий** | внутрь → вне | Логи сессий пишутся в локальный том домена и расходуются снаружи по «watermark подтверждённой загрузки» — квоты, биллинг и аудит считают это источником истины |

Одной фразой: **внутри домена только исполняют, суждение выносится снаружи**. Экземпляр DSH не знает о существовании других тенантов; все межтенантные решения (кого впустить, что можно использовать, что сделано, как удалить) живут на стороне DSH-BOOT.

Аналогия одной строкой: **DSH относится к DSH-BOOT примерно как JVM к Spring Boot** — ядро управляет рантаймом одиночного экземпляра, платформа — мультитенантной корпоративной семантикой.

## Постройте свою бизнес-систему

Написать бизнес-систему на DSH-BOOT = определить четыре типа активов; всё остальное делает платформа:

| Вы определяете | Через | Платформа гарантирует |
|---|---|---|
| **Сценарий (Scenario)** | `presetId + pluginSet + policies` | presetId только добавляется, не меняется (вечная поверхность совместимости) |
| **Инструмент (Tool)** | Единственная точка входа — мост регистрации; всё вне toolAllowlist не регистрируется | Даже вредоносный MCP с новыми инструментами не попадает в видимый набор |
| **Коннектор (Connector)** | Регистрация в каталоге, по умолчанию `untrusted` | Учётные данные хранятся только ссылками; исключения требуют security-ревью |
| **Навык (Skill)** | Три уровня scope: platform / tenant / user | Собирается по тенанту, никогда не пересекает слои |

Минимальный пример (выдержка из контрактных тестов, можно скопировать и запустить):

```js
import { ScenarioCatalog, ConnectorRegistry } from "../../../../packages/control-plane/src/registry/registries.ts";

// Определяем сценарий: presetId + набор плагинов + политики
const scenarios = new ScenarioCatalog();
scenarios.define({
  presetId: "preset-1",
  pluginSet: ["dsh-base"],
  policies: { requireApproval: ["shell"], toolAllowlist: ["fs"] },
});

// Регистрируем MCP-коннектор: по умолчанию untrusted, исключения требуют security-ревью
const registry = new ConnectorRegistry(2);
registry.register({
  serverName: "github-mcp",
  transport: "stdio",
  hosting: "domain",
  credentialRef: "credref-1",
  trust: "untrusted",
  securityReviewPassed: false,
});
```

Бизнес-разработчики **не пишут никакого кода изоляции, аудита, квот или персистентности** — определяют четыре типа активов, остальное предоставляет платформа.

```bash
# 11 контрактных наборов — каждая семантическая гарантия платформы зафиксирована тестом
pnpm contract:llm && pnpm contract:tools && pnpm contract:approval
pnpm contract:ready && pnpm contract:persistence-l1 && pnpm contract:pool
```

## Принципы проектирования

1. **Принуждение исходит только извне домена** — легитимность по слоям определяется при генерации Profile; домен не заверяет сам себя (самоподтверждённый комплаенс = провал).
2. **Гейты принимают только факты извне домена** — отчёты изнутри — только перекрёстная сверка; расхождение, и домен отсоединяется.
3. **Мягкие зависимости никогда не блокируют выполнение** — упали биллинг или общий аудит, выполнение продолжается; ограниченные сбросы + tombstone-записи + дозагрузка.
4. **Не можешь — так и скажи** — каждая незавершённая позиция честно зарегистрирована, никаких выдуманных цифр.
